## B-189 · Monomachine: OJMP may reach the firmware at about twice the value set (open)

- **From:** found in code review for B-179, 2026-10-28; no tester report.
- **What happens:** the page writes OJMP to bits 4 to 7 of the play byte (`mmDeskEdit.cpp`, `mmJson.cpp`), but the knob was measured setting bits 3 to 6 (doc mm-manual-mapping.md, note 6). A page OJMP of n would then reach the firmware as about 2n.
- **Should:** OJMP on the page and on the machine agree.
- **Status:** open. Needs a firmware check of the bit layout before the encoding changes.

## B-179 · Monomachine ARP: a single triggered note does not repeat as expected (open)

- **From:** [Discord #bugs, 2026-10-21](https://discord.com/channels/1557742798936084565/1557745221930848277/1562322234792607875); exact version, OS and host not stated.
- **What happens:** the reporter expects the arpeggiator to repeat with one triggered note, but says it does not.
- **Needed:** ARP mode, speed, range, length and active steps; note length, envelope settings and whether the note comes from the sequencer or a held key. B-180 may affect which ARP steps are actually enabled.
- **Status:** Open for the reported setup. Source/manual semantics already require at least two notes in SID mode; KEY/ADD can repeat one note. Help now explains the distinction and focused preview regressions cover it. No firmware rule was changed without the mode and pattern; awaiting CI.
- **Firmware rule (manual 1-61, 1-62):** KEY plays one held note again and again at SPD until it is released; ADD the same; SID does not start on one note ("When only one key is pressed the arpeggiator is not activated"), on hardware as here, so SID with one note is not a defect. A sequencer trig is a held key: it holds its note to the track's NOTE OFF or next trig (manual 1-27, 1-49; measured, `mmDeskFirmwareTest notelength`). The emulator runs the firmware, so the editor decides only how long the note is held.
- **Cause (editor, 2026-10-28):** the roll gives every new note the draw length, 1/16 by default (`S.rollLen=1`, I-010), written as a NOTE OFF one step after the trig (`MmRoll.setLen`). With KEY or ADD at SPD 6 that NOTE OFF releases the held note after one arpeggiated note, so a single clicked note "does not repeat"; the page's own light notes showed that one note too. The machine's TRIG keys write no NOTE OFF, so on hardware the note is held to the next trig and repeats. The editor sends the ARP settings as they are (op `arp`, mode, speed, range, length, steps); nothing else stops the run.
- **Fix (branch `fix/b179-b174-b027`):** a new note drawn or painted in the roll of a synth track whose arpeggiator is on (KEY, SID, ADD) is held to the next trig with no NOTE OFF (`drawLen` in 70-seq.js); arpeggiator OFF keeps the draw length. Dragging a note's end still writes a NOTE OFF. The roll's tooltip and the KEY/ADD help say what ends the run; guide chapter 15 too. Notes drawn before the fix keep their NOTE OFFs: drag their end to lengthen them. Test: `mmViewTest.js` B-179 (OFF: a NOTE OFF on the next step; KEY and SID: none, the span runs on). CI pending.
- **Also found, not changed:** OJMP is written as bits 4-7 of the play byte (`mmDeskEdit.cpp` arp, `mmJson.cpp`), while the measured knob sets bits 3-6 (mm-manual-mapping.md note 6), so the page's OJMP n reaches the firmware as about 2n. It does not affect a single note; it needs its own firmware check before the encoding changes.

## B-174 · Kit names from a previous SysEx import remain listed (open)

- **From:** [Discord #general, 2026-10-20](https://discord.com/channels/1557742798936084565/1557742800060031060/1562197035418001430), described as the new version; exact version, editor, OS and host not explicit.
- **What happens:** kit names from an earlier SysEx import are still listed. The report does not say whether this follows an update, another import or a reset.
- **To distinguish:** expected persistent machine memory / slots untouched by a partial import, stale library names, or failed replacement. Obtain the chosen import mode, affected slots and before/after names; compare stored kit names with the chooser.
- **Status:** open, needs reproduction details. Do not clear unrelated kits merely because another file was imported.
- **Traced (2026-10-28), both editors (one import job, `mdSyxSession.h` / `mdSyxWork.h`):** an import sends the file's dumps as they are, then reads each slot back; the read-back replies are the desk's dumps too (`onDump`), so the library's names follow. Three ways a previous import's names stay listed:
  1. Slots the new file does not hold keep what the machine holds: as the hardware's SYSEX RECV, and intended (a partial import never clears other slots).
  2. KEEP MEMORY (guide chapter 24): the emulated machine keeps its saved memory across sessions and updates, so an earlier import is still in the machine after installing a new version, until **Start from factory memory** or an Empty Reset. Intended.
  3. **A stale cache, a defect:** with **Read back and compare** off (I-038, remembered per viewer in localStorage) or a slot whose read-back was given up, nothing read the written slots again, and the desk kept the documents it had before the import: the library listed the previous import's kit names for slots the machine now holds otherwise, until the editor restarted.
- **Fix (branch `fix/b179-b174-b027`):** when an import ends, every slot it sent and did not read back is read again by the desk in the background (its load queue, one at a time; over HW MIDI once the cable has carried the dumps): `SyxJob::unread`, `SyxWork::step`, `deskCore::Machine::reread` (both adapters). Test: `syxImportTest` (with the read-back only the given-up pattern is left; without it every kit and pattern sent). CI pending. The reporter's case is likely 1 or 2 unless the read-back was off; still ask which file, mode and slots.

## B-133 · Machinedrum: after a sample is loaded or renamed, live recording records nothing

- **From:** the 0.6 e2e run, 2026-10-13 (`md-seq-live-record`: a step clicked while recording, the machine recorded no trig; `md-seq-live-lock`: no lock). Both passed alone; in the run they came after `md-sampler-rename`.
- **What happened (measured, `mdDeskFirmwareTest <rom> recaftersample`):** once any sample went into the machine by SDS (Rename, which sends the slot's sample again since B-128; Load sample; a dropped file; any ROM slot), live recording looked right (RECORD blinks, the pattern plays, the TRIG key reaches the panel), but the firmware recorded no TRIG key and no knob lock, until the machine started again.
- **The bytes (0.8, bisected by halves over RAM 0x250000-0x2b8000, 15 runs):** the 32-bit cell at **0x28092c**, bytes 0x28092e-0x28092f (0x11a2 against 0x0a6a). It is the head of a doubly linked list of the screen's objects that OS 1.63 keeps (tail cell 0x280928; three nodes of 924 bytes at 0x2811a2, 0x280e06, 0x280a6a; the code that edits it is at 0x213450 unlink and 0x2134ac append, both under a lock). The main screen's list is those three nodes. The "RECEIVING SAMPLE" screen, opened by the SDS header (`f0 7e 00 01`) and closed some seconds after the last packet, takes the three out (0x22ed00) and puts its own node 0x28153e in, and on leaving (0x219f72) takes that out and puts the three back. The OS's unlink copies a node's PREV link into the head; the first node's PREV is the old tail (0x280a6a, left by the append that built the list), so the swap ends with head = tail = 0x280a6a, a list of one node. Recording needs the three nodes (the TRIG key and the knob still reach the panel, the screen that records them is not on the list).
- **Cause:** the OS's own bug in the receive screen's swap, not our sender (the SDS handshake is by the book; every transfer leaves the same state). The emulator runs the OS as it is, so a real Machinedrum with OS 1.63 very likely does the same (not tried: no machine); a restart puts the list right.
- **Fix:** none, by decision (Radek, 2026-10-16): the emulator keeps the hardware's behaviour. A repair that put the head cell back (a small `ScreenListFix` in `Hardware::processAudio`) was built, passed `recaftersample`, the four journeys in shuffled orders and the stage 5 goldens, and was removed again.
- **How it was found:** bisecting the RAM that brings recording back (0x250000-0x2b8000) by halves ended at 0x28092e-0x28092f; a write watch on the cells with the program counter and return address showed three writes to the head cell, all in the unlink at 0x213450 called from 0x22ed00 (the swap at the header); the append at 0x2134ac and the exit at 0x219f72 put the three nodes back without setting the head.
- **Test:** `mdDeskFirmwareTest <rom> recaftersample` now documents the firmware: without a sample the TRIG key is recorded, after one it is not (both pass). It is not in the gate list. `md-sampler-rename` and `md-drop-sample` stay `alone: true`.
- **Status:** open: a firmware bug in OS 1.63; the emulator keeps the hardware's behaviour (Radek, 2026-10-16); workaround: restart the editor after loading a sample (the 0.7.0 release-note text stays).

## B-054 · A project with a damaged flash image can hang the audio thread (seen once, in a probe)

- **From:** the audio-thread spike checks, 2026-10-10: a probe loaded a project whose stored flash was corrupted on purpose at sector 6.
- **What happens:** the audio thread hung for good while holding the device lock: the 68k pushed into DSP1's full host-port queue, which blocks on the same thread that would empty it. The DAW's audio stops.
- **Cause (0.5.1, reproduced, `mdDamagedFlashFirmwareTest`):** three places where the one emulation thread waits for a DSP that only it can move. Sector 6 (0x060000) is the OS: the project's CRCs are over the stored bytes, so the loader took the image and the firmware ran it. With the sector XORed, zeroed or erased, a DSP runs the garbage the OS uploads, its PC leaves P memory and `onInvalidPC` halts it: no instruction runs and no cycle passes for it, and the scheduler (`schedStep`, the catch-ups, the inline host-port loops in `md::Dsp`) waited for its cycles, sleeping 1 ms a turn, for good (`sample` of the hung test: `Hardware::advance` > `schedStep` > `DSP::onInvalidPC` > `sleep_for`; hangs 1.0-1.2 s into the start, 3 of 4 patterns of sector 6, sectors 3-10 the same). The probe's way in: a DSP that stops reading HRX (halted, or running a loop of its own) while the ColdFire writes on; the ring holds 8192 words, the 8193rd `writeRX` waits in its semaphore. The firmware itself waits for TXDE before a store, so only a ColdFire running garbage gets there; the host-command ring (32) the same way.
- **Fix (0.5.1, `fix/0.5.1-b052-b054`):** a halted DSP (`DSP::isHaltedAtInvalidPC`, `md::Dsp::halted`) is parked by the scheduler as a DSP not yet booted is, the catch-ups and the inline host-port loops skip it: the rest of the machine runs on (the halted DSP's audio is silent). A ColdFire word that finds the DSP's receive ring full, or a host command that finds its ring full, is dropped and counted (`droppedHostWords`, a `[md] DSP1 stopped reading its host port` line at the first and each power of two) instead of waited for. The loader puts the ROM's bytes back in any project flash sector below the sample area that is not the ROM's (`md::restoreFirmwareSectors`, 0x000000-0x1fffff: OS 1.63 never writes there; measured, the factory initialization, SDS imports and the UW test write 0x2c0000-0x7bffff only) and says so on stderr; sample sectors stay as the project holds them. None of the three is reached by a running firmware: the goldens are bit-exact (30/30, speed-ups on and off, exact-ESSI).
- **Tests:** `mdDamagedFlashFirmwareTest` (ctest, FirmwareTest; each case on a worker under a 20 s no-progress watchdog): `queue` (DSP1 running a loop of its own, its ring filled, 16 ColdFire stores: dropped and counted; then halted, 64 stores and host commands), `halted` (the machine started on the damaged image as it is: runs 15 s with a halted DSP), `loader` (the image as a project: sector 6 is the ROM's again, the firmware takes MIDI, no DSP halted). With the three fixes off all three hang (`queue` at the first store, `halted` and `loader` at 379 blocks, 1.1 s); with them all pass. `mdStateTest`: the restore (one OS sector back to the ROM's, the sample sector kept, nothing to do on a clean image).
- **Not checked:** whether a real project can reach a damaged OS sector (none seen); the Monomachine's state holds no OS sectors (its DigiPRO window only), its DSPs get the same guards.
- **Status:** fixed in 0.5.1 for 0.5.1.

- **From:** Discord tester A, 2026-10-08, MacBook Pro M1, Ableton Live, 0.3.3.

The cache that should make this happen once per computer was never kept: the editor's status requests (the Song status is not on the read-only list) reached the machine while it formatted, which counts as outside use and disqualifies the capture. Reproduced with 0.3.1 and an empty data folder: one start-up animation, `[MD] factory flash preparation complete; rebooted in process`, a second animation, no cache; Radek's own data folder has never had one, so every start without a saved project did this (a new plug-in instance in a DAW, an app with no saved state). His own first-start log was overwritten by a later start; his migrated settings, started again with 0.3.1 in an empty data folder, restore with one start-up.
- **Fix:** the machine that formats its flash is "loading" for the page (the start-up card says Preparing…, without its LCD) and the editor does not talk to it, so the cache is kept; the start-up animation shown is the one after it. The next start has no preparation at all. Test: `mdFirstStartFirmwareTest` (needs the ROM).
- **Status:** fixed for 0.3.2.
- **Follow-up, 2026-10-08:** `mdSessionNoRomInstallFirmwareTest_md` and `mdSessionNoRomManageFirmwareTest_md` failed on main with "lifecycle still 'loading'". Not a stuck machine: a ROM installed from the start-up card into a data folder without the factory cache gets the same preparation (about 15 to 20 s of "Preparing the Machinedrum…", then one start, cache kept), and the tests looked 15 s after the first run took MIDI, inside it. The tests now wait for the preparation to end and check one preparation, the cache kept, REPLACE and REMOVE-then-reinstall without a second one; each run has its own temp folder (they raced under `ctest -j`).

## B-001 · Plug-in window too big in Ableton Live

- **From:** Discord beta tester A, 2026-10-07.
- **Setup:** Ableton Live, macOS 12, Apple M1 (the "66 %" in the report was Live's CPU meter, see B-005, not a zoom). Machinedrum Editor plug-in, MIX workspace.
- **What happens:** the page is drawn larger than the plug-in window. The right part (track 13 onwards, the header's right side) and the bottom are cut off. The page cannot be zoomed out, so the settings cannot be reached.
- **Should:** the page fits the plug-in window at any host zoom, the window can be resized, and the user can zoom the page (a control and ⌘− / ⌘+).
- **To check:** how the window size and the web view's zoom follow the host's scale (Retina and non-Retina, WKWebView on macOS 12); `mdStudioWebZoom.mm`, `mdWindowFitTest`; the Monomachine Editor; Logic, Bitwig and Reaper.
- **More evidence (second screenshot, same tester):** the header LCD has no inner borders, the transport buttons are not boxed, and SETUP (UNDO/REDO/MKI) is cut off; on Radek's newer macOS all of it renders correctly.
- **Likely cause:** macOS 12's system WebKit (Safari 15 engine) does not support some CSS the page uses (e.g. container-query units, color-mix), so those rules are dropped. Fix: fallbacks for the oldest supported WebKit, and an honest minimum macOS version.
- **Update 2026-10-07:** the tester says the cut-off window was their own setting (the editor size is in the right-click menu). The missing LCD borders are still real (old WebKit, see above).
- **Cause, rendering:** the editor's web view is the system WebKit, the one the installed Safari brought; macOS 12 with Safari 15 is WebKit 15. Both stylesheets use `color-mix()` (WebKit 16.2) about 70 times (no container queries, no `@layer`, no nesting): WebKit 15 drops each declaration that has one, and the LCD's rule variable (`--lrule`, a mix) makes every LCD divider invalid; that is the second screenshot. `:focus-visible` (WebKit 15.4) drops whole rules that list it (hover states), and `structuredClone` (15.4) is missing for the Monomachine page. The play head (B-008) is the same cause.
- **Cause, size:** the window size was the tester's GUI Scale, but nothing kept it on the screen: a plug-in's editor opened at whatever size was set or last used (the standalone's included), larger than a 1440 x 900 screen, its right part, SETUP and resize corner off the screen; and the page had no zoom of its own.
- **Fix (branch `fix/plugin-window-fit`):**
  - `skins/shared/deskCompat.js`, first in both pages' `<head>`: where the engine lacks `color-mix()` or `:focus-visible` it rewrites the stylesheets before the first paint (each mix as the same `rgba()`, through channel variables beside each colour variable, so themes and plates still apply; `:focus-visible` as `:focus`), and adds `structuredClone`. A current engine keeps the stylesheets as written. Forced on (`?compat=force`) in Chrome it draws the MD page pixel for pixel like the original. `deskCompatTest.js` checks every mix in both stylesheets is rewritten. Left alone (an older WebKit skips them, nothing breaks): four `:has()` rules (WebKit 15.4) and `subgrid` (16) in alignment details, `scrollbar-gutter`, `overscroll-behavior`, `accent-color`.
  - A plug-in's editor is never larger than its screen (less 64 pt for the host's bars): `windowFit::fitPluginSize`, applied once the host shows the window, not stored as the user's size.
  - The page always fits its window: narrower than 1440 or shorter than 720 CSS px zooms it out, larger both ways zooms it up (`mdPageZoom.h`); where the web view has no `pageZoom` (macOS 10.15 and older) the page's CSS zoom does the same.
  - The page's own zoom: **Page Zoom** in the editor's menu (right-click on the page's header, the standalone's Editor menu) with Zoom In / Zoom Out / Actual Size and 50-200 % steps, and ⌘− / ⌘+ / ⌘0 on the page (`deskZoom.js`, the `pageZoom` command), remembered in the editor's config.
- **Minimum macOS:** 12 (Monterey), any Safari 15 or later. macOS 11 with Safari 15 should work the same (not tested); macOS 10.15 and older lack flex `gap` and `inset` (Safari 14.1) unless Safari was updated, and are not supported. The build's deployment target (10.13) is not a claim.
- **Status:** fixed for 0.3.2. To confirm with the tester: Safari's version (Safari > About Safari).
