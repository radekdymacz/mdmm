# Review 5: real-time and UI performance (static, read-only)

Branch codex/native-audio-engine, HEAD 2c59fdb95. Read first: RESEARCH-emulation-cpu.md (levers, refuted list, section "Around the core"), md_mm_performance_diagnostics.md, DESIGN-edit-flow.md. Nothing below repeats a refuted lever or the six "around the core" items already measured. Nothing was built or run; every finding was verified by reading the cited lines.

Overall: the audio path is already unusually well hardened (try-lock publishers, chunked 64 KiB lock holds for the memory watch, lock-free ingress queues, allocation counters, paced and coalescing edit stream). No must-fix found. The remaining risks are a freeze path with no watchdog, thin headroom at small buffers, and page/idle cost.

## Findings

### 1. [should-fix, release risk] Audio thread has no budget or watchdog; a stuck machine freezes the host
- `Hardware::advance` loops `while(schedStep()) {}` (source/elektron/md/mdLib/mdhardware.cpp:1838) on the audio thread, inside `Plugin::process` which holds `m_lock` (synthLib/plugin.cpp:111-122). The only exit is that every component reaches the target clock. B-054 added a guard for a halted DSP (mdhardware.cpp:1403-1407) but there is no wall-clock or iteration cap.
- The doc's own note ("Also seen", RESEARCH-emulation-cpu.md ~line 510): a corrupted-flash project hung the audio thread for good, holding the device lock, because the ColdFire pushed into DSP1's full `RingBuffer<TWord,8192,true>` (dsp56300/source/dsp56kEmu/hdi08.h:241-242; `m_dataRX.waitNotFull()` at hdi08.cpp:305, `waitNotFull` at :471, `waitNotEmpty` at :451). Status in the doc: "not reproduced with a real project", not fixed. While the lock is held the message thread (editor timers, the 1 Hz boot sample, state save) also blocks, so the whole DAW appears dead, not just this plug-in.
- Impact: low probability, worst severity (host freeze, lost project). For a 1.0 that loads user-supplied ROMs and project state this is the one failure that is not a glitch.
- Fix: (a) give `advance` a cycle/iteration budget per call (for example 8x the block's expected UC cycles) and, when exceeded, mark the device invalid (`isValid()` already routes to `m_callbackDeviceInvalid`, plugin.cpp:131) and output silence; (b) at the md call sites that feed HI08 (mdhardware host pump), use a non-blocking push (drop and count) as the doc proposes. Cheap check in the loop: one counter compare per `schedStep`.

### 2. [should-fix, headroom] Zero latency blocks by default with 55-70 % of the block already used at 128 frames
- `Device::getDefaultLatencyBlocks()` returns 0 (mdLib/mddevice.h:139; the synthLib default is 1, synthLib/device.h:75). The emulation therefore runs synchronously inside every host callback, so any spike is a drop-out.
- Measured baseline (DESIGN-edit-flow.md ~line 148, before the 0.5.x speed-ups): 60 % (MD) and 68-74 % (MM) of each 128-frame block at 48 kHz, with 0-27 overruns per 3 s and no edits, max 3.2-18 ms; 512 frames had none. Speed-ups since gave -16 to -19 % (RESEARCH doc, step 1), so roughly 50 % / 55 % now, but no fresh overrun count is recorded after the speed-ups. Edits, dumps, JIT warm-up (first blocks up to 3.4x, "around the core" item 3) and the first-run candidate machine (up to 6.9 ms in one block) all land on this path.
- Impact: audible drop-outs for users who run 64/128 buffers (the default in Live and Logic low-latency setups). It is the highest-probability 1.0 complaint.
- Fix: re-measure overruns per 3 s at 64/128/256 on the shipped build and put the number in the release notes. Consider defaulting `latencyBlocks` to 1 when the host buffer is under 256 (the config key `latencyBlocks` already exists, mdPluginProcessor.cpp:~560), or auto-suggest it from the CPU meter's worst-block reading when it crosses ~85 %. Needs Radek's decision (it changes reported latency).

### 3. [should-fix, page CPU] GEN/MUTATE drag, wheel, rotate and tempo drag are not "held", so each document triggers a full page re-render
- `HOLDS = new Set(["value","editor","lane","l2","chop","song","paint","mutePaint","select"])` (skins/mdStudio/mdDeskRender.js:24). The page also begins the gestures `"gv"` (mdDeskGestures.js:51), `"wheel"` (:75), `"rotate"` (mdDeskComforts.js:82) and `"bpm"` (mdDeskGestures.js:285), which are missing. `interacting()` is false for them, so `scheduleRender()` (mdDeskRender.js:30-41) runs the full `render()` for every relevant `doc` that lands mid-gesture.
- DESIGN-edit-flow.md:98 measured this and left it open: "Edits not held by a gesture (a wheel run, a GEN or MUTATE value drag at 30 a second) still re-render the grid at every document: about 50 % WebContent and more than a core of GPU, almost all of it the step cells' box-shadows... Next: hold the renders for those gestures as the lane does". The lane drag, which is held, costs 17-20 % WebContent.
- Impact: ~2.5x WebContent CPU and a GPU core while dragging GEN or MUTATE values or using the wheel, competing with the audio thread on the same machine. The MM page was not measured at all.
- Fix: add the four kinds to HOLDS (the gv handler already updates in place via `renderTop(); redraw()`, mdDeskGestures.js:46, and `Held.onEnd` flushes the pending render, :28). Check the MM page (mmMockup.js render path) for the same omission.

### 4. [should-fix, idle cost] Session timer runs at 125 Hz per instance for the processor's whole life, editor closed or not
- `DeskSession::create` does `session->startTimer(8)` (mdDeskSession.cpp:184, g_stepMs mdDeskSession.h:39). `step()` (mdDeskSession.h:~386-470) calls `m_engine->step` unconditionally before any `pageSeen()` test. For the MD emulator engine that is `readTelemetry()` (mdStudioLink.cpp:~190-250: a `FrontPanelPublisher::read()` mutex lock plus a full `FrontPanel` copy each step, a vector push per chain slot), `LcdFeed::step`, `readWorkingKit`, `drainParameterChanges` (mdSessionMd.cpp:76-101), then `m_learn.enforce()`.
- A DAW project with 8-16 instances and all editors closed is the normal case. That is ~1000-2000 message-thread wake-ups a second for no visible effect, on the same thread as the host's GUI, plus battery. The panel mutex is also contended with the audio thread's `tryPublish` (it only skips a publish, so no glitch, but it adds avoidable stale-frame churn).
- Fix: keep 8 ms only while `m_desk->pageSeen()`; otherwise run at 50-100 ms (the things that must still happen without a page are `takeMidiIn`, probe, followHost at 2 s, memory-version; all tolerate it). Skip the panel copy when no page is attached.

### 5. [should-fix, UI] Forced reflows inside every sequencer render (`alignLock`)
- `renderPage()` ends with `alignLock()` (mdDeskRender.js:~127-150). It interleaves `style` writes (`removeProperty`, `setProperty`, `marginTop`) with ~12 `getBoundingClientRect`/`getComputedStyle` reads, and repeats the `ch.style.marginTop`/`height` pair twice. Each read after a write forces a synchronous layout of the sequencer workspace (hundreds of cells).
- Impact: adds several ms of layout to every full render of the seq workspace (also on each pattern, kit or host-tempo document, since `host` messages call `scheduleRender`, mdDeskRender.js:70). Page JS was measured at ~1 ms per render in Chrome without this being isolated; WebKit layout of the grid is the larger part.
- Fix: do all reads first, then all writes (one reflow); or run `alignLock` only on workspace change and resize/zoom, not on every document. The second duplicated block (the last two lines) can be dropped if the first pair converged.

### 6. [later, startup and open cost] The whole page is rebuilt as a ~2 MB string on every editor open
- `WebPageHost::bundle()` (mdWebPageHost.cpp:381-411) base64-inlines four TTFs (540 KB on disk, ~720 KB in the page, skins/mdStudio/fonts), inlines every script (MM page ships mmMockup.js 651 KB and mmAdapter/mmView ~80 KB; MD ~600 KB of page JS), and `load()` writes it to a temp file (`replaceWithText`, :404-405). Done on the message thread each time an editor opens; WebKit then re-parses it all.
- The temp file `gearmulator-*.html` is deleted in the destructor (:317-318) but a crash or host kill leaves ~2 MB behind each time.
- Fix: build the bundle once per process (static cache keyed by page name); convert fonts to woff2 (the CSS already supports it, :388) for roughly a third of the bytes; sweep stale `gearmulator-*.html` files at start. Measure `page loading ... bytes` and `page up ... ms` lines the host already logs before deciding if it matters.

### 7. [later, audio-thread allocation, counted and accepted] SysEx on the audio thread copies a pmr vector
- `SMidiEvent` keeps 64 bytes inline (synthLib/midiTypes.h:41); anything larger (every desk pattern/kit dump, 5 KB) heap-allocates when copied (`Plugin::processMidiInEvent` increments `m_realtimeAllocationFallbackCount`, plugin.cpp:393-399; processor.cpp:~783 counts the same for host MIDI). `ScheduledMidiQueue::push` stores a copy and `push_heap`/`pop_heap` move `Entry` objects whose pmr allocator does not propagate (mdLib/mdscheduledmidi.h:50-52,71-74), so moves between slots can copy the bytes again.
- Impact: tens of microseconds per dump under the device lock, at most ~5 dumps/s (stream cap, deskStream.h) so 1-2 % of a block at worst, but malloc latency is unbounded in theory.
- Fix (post 1.0): keep the sysex bytes in a preallocated arena in `ScheduledMidiQueue` and heap-sort indices; or reserve `sysex` capacity 8 KB on the ring slots (the ring is 1024 events, so that is 8 MB, too big; arena preferred).

### 8. [later, audio-thread locking] Host MIDI path takes a mutex the message thread can hold while waiting for the device lock
- `Plugin::addMidiEvent` takes `m_lockAddMidiEvent` (plugin.cpp:37) and, if the 1024-slot ring is full, takes `m_lock` while holding it (:39-41). The audio thread calls this per host MIDI event (jucePluginLib/processor.cpp:~783 `addMidiEvent(ev)` -> :~86), so it can wait on a message-thread caller that is itself waiting for the audio thread's `m_lock`. Only when the ring is full or the mutex is contended; the window is a few instructions otherwise. `m_hostFeedbackMutex` is also locked once per block (processor.cpp:871) against the message thread's MIDI learn writes.
- Fix: make the host-event path `try_lock` and fall back to the already-existing `tryAddRealtimeMidiEvent`/`insertMidiEvent` route; use a small SPSC ring for host feedback.

### 9. [later, first run] Factory-flash capture hashes 64 KiB per block on the audio thread
- `advanceFactoryFlashCapture` (mdhardware.cpp:681-751) copies one 64 KiB sector and runs a byte-serial FNV-1a over it every block until the baseline is complete (:723-727), roughly 64 K dependent multiply-adds, estimated 70-100 us per block, repeated for every sector of the sample flash. Once per installation (after 10 s of machine time), plus the already-documented second-machine candidate at 15 s (item 3 in the "around the core" table).
- Fix: copy on the audio thread but hash on the message thread/memory thread from the finished baseline, or use a wide hash; the fingerprint is only compared at the end (:735, :743).

### 10. [later, memory] Large reserved buffers per Hardware instance, doubled during state restore
- `ScheduledMidiQueue<16384>` reserves 16384 entries each holding an `SMidiEvent` (64-byte inline pmr storage plus vector) in `m_events.reserve(Capacity)` (mdscheduledmidi.h:41, mdhardware.h:497): estimated ~2.5-3 MB per machine, for a queue that the pacing keeps in the low hundreds. Plus flash baselines (`g_romSize` x baseline, cache, pending image), 1 MB patch RAM scratch x2 and the MM user flash scratch in the memory watch (mdPluginProcessor.cpp:1989-1995), and `m_deferredPreparedState` holds a second full Hardware during restore (mddevice.cpp:640-645). Estimates only, not measured RSS.
- No leak found on open/close: destructor order is explicit (mdPluginProcessor.cpp:~620-630), the memory thread is joined (:1325-1330), timers stopped.
- Fix: cut the scheduled queue to 1024-2048 (overflow is already counted and refused, mdhardware.cpp:1904) and read RSS per instance with 1, 8 and 16 instances before 1.0.

### 11. [later, Linux only, marked not tested] Idle polling by script element at 8 ms
- With `?recv=file` the page loads `.recv-N.js?t=` scripts in a loop and on error retries every `POLL_MS = 8` (skins/shared/deskBridge.js:25,70-80), so an idle page makes ~125 failed file loads a second. Windows and macOS use the direct path and are unaffected.
- Fix: back off to 30-50 ms when no batch arrived for a while, or have C++ signal availability.

### 12. [later, defensive] Dropped scheduled MIDI is silent
- `Hardware::scheduleMidi` returns false and increments `m_scheduledMidiOverflow` when 16384 entries are queued (mdhardware.cpp:1902-1906), but the count is only read by an accessor (mdhardware.h:224), not shown in the CPU meter or log. By then `Plugin` has already popped the event, so an edit is lost with no sign. Unreachable at the current pacing, but a runaway host (looped MIDI out, flood 6 in DESIGN-edit-flow.md) would trigger it.
- Fix: surface the count in the boot/CPU report line and the page's error toast.

## Checked and fine (no action)
- Realtime hygiene around the lock: memory watch holds `m_lock` in 64 KiB pieces and measures it (mdPluginProcessor.cpp:1983-2060); one-hold atomic copies only at flush/close (~0.1-0.3 ms, as documented); `FrontPanelPublisher::tryPublish` and `tryRead` are try-locks (mdfrontpanel.cpp:233-252); output meter, CPU meter, boot counters are relaxed atomics (mdBootDiagnostics.h:19-36, processBlockStarted/Ended); `getenv` only in constructors or a function-local static (mddeskdevice.cpp:37), none per block.
- Edit stream (deskStream.h): requests deduped (`ask`), dumps of one document replaced while waiting, values and value SysEx coalesced per key, held queue only while a sample transfer runs, ingress rings fixed-size and refuse rather than grow (mdrealtimemidiqueue.h). The queue is bounded by user action; a full-backup import queues a few MB by design and drains at 125 KB/s stopped.
- Message-thread timers: page editor 30 Hz with a bounded flush (mdPageEditor.cpp:162,399-430, `layout()` is idempotent and `setWebPageZoom` compares before it sets, mdStudioWebZoom.mm:32); status messages are throttled (cpuLoad 250 ms, outputLevel 250 ms, midiHeld 32 ms, host tempo 100 ms). The old panel editor's 16 ms and 33 ms timers (mdEditor.cpp:90-93) belong to the skin editor, not the page editor.
- Release flags: PGO profile not stale (git tree hashes of mdLib, mc68k, dsp56kEmu equal the values in pgo/mdmm-macos.json). Diagnostics, journeys and self-tests are excluded from release binary data (mdmmPlugins.cmake:124-128,174-199); `MD_TRANSPORT_DIAGNOSTICS` defaults to 0 (mdtransportdiagnostics.h:7-9); the edit-flow driver is behind an OFF option. A grep for `std::isfinite/isnan/isinf` in elektron, synthLib and jucePluginLib found no remaining uses (baseLib::isFinite is used; mdLibTest builds the NaN checks with fast-math off). `-Ofast`/`/fp:fast` and `-fno-lto` on GCC are set in base.cmake:12-32,69-70,115-116 and are covered by that rule.

## Priority order for 1.0
1. Finding 1 (watchdog) and Finding 2 (headroom number plus default) are the only ones that can lose a user's session or produce audible failures at default settings.
2. Findings 3, 4 and 5 are small, local JS/C++ changes with measured or easily measured savings.
3. Everything else can follow 1.0.
